# NavAssist — SunnyPilot release-mici / Comma 4 port

This branch ports the four-layer Tesla NavAssist path from
`Sniper-Eon/openpilot:navassist-jetlink-tesla` onto
`sunnypilot/sunnypilot:release-mici`.

## Four-layer design

1. **Phone / JetLink ingress** — receives route, location, maneuver and lane
   guidance from the paired mobile app through the NavAssist v3 protocol.
2. **Visual lane topology** — consumes the C4 `VISION_STREAM_ROAD` camera,
   `roadCameraState`, `liveCalibration` and C4 front-camera intrinsics.
3. **Navigation lane intent** — matches route maneuvers to local visual topology
   and publishes typed lane/turn intent. Navigation intent is not lane-change
   authorization.
4. **Tesla control integration** — the modeld Tesla path combines visual
   boundary blocking, Tesla OEM feedback, blind-spot state, driver override,
   turn-entry qualification and the existing SunnyPilot AutoLaneChangeController.

## C4-specific changes in this port

- `lane_topologyd` uses `VISION_STREAM_ROAD`, `roadCameraState`,
  `liveCalibration` and `DEVICE_CAMERAS[...].fcam.intrinsics`.
- Manager startup is gated to physical `mici` (C4) devices; the control-facing
  observers additionally require a Tesla vehicle and onroad state.
- The non-Tesla modeld path uses a preserved copy of the release-mici
  `LegacyDesireHelper`; the new NavAssist-aware DesireHelper is selected only
  for Tesla.
- Cereal schemas, event IDs, services, service registry and pairing Params are
  added for NavAssist, lane topology and navigation lane intent.

## Port gaps found during the C4 static audit

- **C4 UI is partially integrated.** The Mici developer settings now show
  NavAssist phone-pairing status and provide an offroad reset confirmation.
  The lane-topology/navigation HUD from the source branch is still not ported
  into the C4 onroad UI.
- **Both model runners now contain the Tesla NavAssist control path.**
  The `sunnypilot/modeld_v2/modeld.py` tinygrad runner and
  `selfdrive/modeld/modeld.py` stock runner both consume typed navigation
  intent and lane topology, apply visual boundary blocking and Tesla OEM
  safety gates, and pass the resulting permissions into the shared
  `DesireHelper`. Non-Tesla stock-runner behavior stays on the preserved
  `LegacyDesireHelper` path. This is source-level integration; runtime and
  closed-course validation are still required.

## Known limitations — not yet C4-validated

- The Sniper branch's Tesla OEM decoder expects CAN bus 1 and 8-byte frames at
  addresses `0x239` and `0x399`. The C4 Tesla harness/bus mapping has not yet
  been confirmed by C4 CAN capture or replay. Missing/stale/invalid OEM data
  must remain fail-closed; do not treat a successful import as proof of CAN
  compatibility.
- ARS408 `radarTracks` is not a validated service in this release-mici C4
  target. Radar-based efficiency overtaking is therefore disabled in
  `nav_lane_intentd` until a compatible radar source is validated.
- `speed_controller.py` is ported as a module but is not connected to the
  release-mici longitudinal planner. Navigation speed control is not active.
- The optional standalone diagnostics recorder is not registered as a process.
- Cap'n Proto generated C++ artifacts have not yet been regenerated by the
  target build toolchain after the schema changes.
- The imported test suites have not yet been executed on this branch. No
  successful compile, C4 installation, onroad startup, CAN replay, or
  closed-course validation is claimed.

## Safety boundary

Navigation data does not issue steering, acceleration, brake, or CAN commands.
It cannot independently grant a lane crossing. Solid-line/road-edge evidence,
blind-spot state, driver override, stale data and OEM safety vetoes remain
independent blockers. Do not enable automatic lane changes on public roads
until C4 camera, CAN, process startup and closed-course tests have passed.
